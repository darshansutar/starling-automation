## Start and resume

Use a separate project for a new source. For existing projects read status/next without reinitializing. Before building or generation ask source mode, style source and speaker voice IDs/names; read-only intake inspection can identify cast and download references. Record actual answers and inspected artifacts in intake.json. Existing project answers may be reused when source/version and choices match; never fabricate a retrospective confirmation.

```powershell
python pipeline/runtime.py --project projects/PROJECT init --title "Project title"
python pipeline/runtime.py --project projects/PROJECT status
python pipeline/runtime.py --project projects/PROJECT intake intake.json
python pipeline/runtime.py --project projects/PROJECT next
```

New projects default to all_ready_once and current reference-mode routing. Existing projects retain their history; recording intake adopts the current policy for future work. It does not migrate manifests or resubmit jobs. Reconcile existing source/image/audio/prompt receipts and job versions before reuse. Missing/changed intake blocks new acceptance/submission.

## Visual and render handoff

Approve a scene master before panels for each continuous location. Record camera axis, named screen positions, seating/standing orientation, furniture dimensions/placement, fixed landmarks, prop state and lighting. The first panel uses visible characters, environment, visible props and scene master last. Later panels use the same required appearance references with the previous approved panel or scene master last. Reject swaps/mirroring, camera-axis crossing, changed sitting orientation, furniture growth and background drift at image review.

Use the mandatory narration storyboard method throughout. Choose a 1x2 or 1x3 board from the accepted audio-led semantic beats, with one distinct source-supported purpose per panel. A narration panel may move to another supported character, environment, prop or consequence when the spoken meaning requires it; do not force every panel into the dialogue location. Apply full scene continuity at the final panel before dialogue and wherever the same moment/location continues. Do not use arbitrary duplicate frames or unsupported filler. Dialogue animation passes exactly one approved clean full-frame scene plus accepted audio. During every spoken line the camera is a pixel-locked static tripod: zero pan, tilt, zoom, push/pull, dolly, track, orbit, crane, handheld/stabilization drift, automatic recentering/reframing or focal-length change. Only lips, eyes, blinks, breathing and restrained source-supported gestures move. Any camera movement or reframing is a blocking failure even when identity and lip-sync are otherwise correct.

Narration boundaries follow position in the node:

- **Before dialogue** (including the end of narration between two dialogues): design the final narration panel together with the following clean dialogue scene so the cut into lip-synced dialogue is continuous. The final panel shows the upcoming speakers, lips closed, in their dialogue positions, using the same scene master, environment/time, lighting, camera axis, furniture/prop state and recorded screen positions. Compare them side by side and record a passed narration_dialogue_handoff in the dialogue render plan.
- **After dialogue** (including the start of narration between two dialogues): use the storyboard mainly for source-supported B-roll and subject action that justify the narrated scene. No handoff with the preceding dialogue scene is required; keep identities, style and time of day consistent, and keep the dialogue geography if a panel returns to that location.
- **Opening and ending narration** use the normal storyboard method driven by the accepted narration audio.

Transport approved originals through Google Drive under confirmed `darshan@en2.ai`: record file ID, fetchable image URL and hash; upload that URL through EN2; record returned upload name and visually compare it with the original. The payload uses returned upload names in visible-character, environment, visible-prop, composition-anchor order. New production always follows the approved scene/storyboard input; do not substitute an extracted video frame.

Follow [visual routing](../starling-animation-pack/references/visual-routing.md). Every narration clip uses the mandatory storyboard method: a black-and-white 1x2 or 1x3 storyboard with SHOT/time/CAMERA/ACTION labels below all pictures. A single full-frame narration scene is invalid. Inspect all pictures and labels, then write a detailed description of each actual panel and its exact action/camera/timing using the current reference prompt template. Select attachments under [scene-matched reference selection](../starling-animation-pack/references/reference-bundle.md): only visible character identities and relevant props, in applicable group order; environment-only clips use environment and composition anchor. Shared multi-shot requests use the union of visible references while keeping per-shot visibility explicit. Rebuild reference indexes and remove omitted-subject prose after changes. Keep a clear gap between adjacent people. Every storyboard panel must have a distinct source-supported purpose while preserving continuous geography. Dialogue retains exactly one clean-scene ref, accepted speech and existing turn mapping. Record picture boxes, hashes, Drive/EN2 upload checks, measured audio mappings and shot_inventory_match. Narration plans use storyboard_1x2/storyboard_1x3 with shot_count minus one strictly increasing cut_times. Follow [buffered timing and visual review](../starling-animation-pack/references/timing-and-visual-review.md): each narration/establishing shot gets 1–2 seconds of buffer, with identical generated ranges and hard-cut times in printed storyboard labels and prompts. Save separate required edit timing and per-shot source_spans for trimming. The runtime validates structure, not visual truth. Reconcile older narration plans before new submissions; preserve paid IDs and media.

Before accepting any storyboard, validate the physical logic of every depicted task: participant count and roles, facing direction, action axis, object contact/support and cause-to-effect sequence. Reject attractive but impossible staging. For a correction, create a new image version, remove the rejected version from active manifests and re-run downstream receipts before upload or animation. Use 1K-class images by default for planning references and storyboards; record actual dimensions. Treat 4K as an explicit opt-in or documented downstream requirement, never an assumed label.
